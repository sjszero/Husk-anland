# evidence 30 — `nr-tools check-elf`：用同余关系判定能不能跑，而不是看设备标签

日期：2026-11-22 21:25 CST
工具：`nr-tools check-elf`（本轮新增，Rust）

## 判据

内核 execve 时对每个 `PT_LOAD` 用 `ELF_PAGESTART(p_offset)` 做 `mmap` 的文件偏移，
`mmap` 要求该偏移按 `PAGE_SIZE` 对齐，否则 `EINVAL`，整个 execve 失败。真正的判据是

```
p_offset ≡ p_vaddr  (mod PAGE_SIZE)      # 每个 PT_LOAD
p_align  >= PAGE_SIZE                    # 下界声明，越大越安全
```

与"设备是 4K 还是 16K"不是一回事：64K 对齐的产物在 4K 内核上照样能跑。

## 实测（本机，2026-11-22）

```
$ nr-tools check-elf bash.elf libc.so.6 ld-linux-aarch64.so.1 libhuskapp.so libld.so
/tmp/devlibc.so                          p_align=0x10000  loads=2  4096:ok 16384:ok 65536:ok
/tmp/husk/bash.elf                       p_align=0x10000  loads=2  4096:ok 16384:ok 65536:ok
/tmp/ld-device.so                        p_align=0x10000  loads=2  4096:ok 16384:ok 65536:ok
…/libhuskapp.so                          p_align=0x4000   loads=3  4096:ok 16384:ok 65536:FAIL
…/libld.so                               p_align=0x10000  loads=3  4096:ok 16384:ok 65536:ok

checked 5 ELF file(s)
    4096: all congruent
   16384: all congruent
   65536: 1 file(s) would fail to exec
```

结论：

- **guest 用户态（bash/libc/loader）本来就 64K 对齐**（GNU ld 的 aarch64 默认），
  所以在 16K 甚至 64K 内核上都不需要额外改造——这是查出来的，不是猜的。
- **我们的 `libld.so`（embed 产物）三种页大小都满足同余**，可以在 16K 设备上用。
- **`libhuskapp.so` 是 NDK 29 默认的 16K 对齐**，在 64K 页内核上会失败。Android 目前
  只有 4K/16K，所以不影响；如果要覆盖 64K，把链接参数写成 `max-page-size=0x10000`。

## 工具行为

- `nr-tools check-elf <elf|dir>... [--page N]...`：默认对 4096/16384/65536 三个页大小
  各判一遍；有任何一个 PT_LOAD 不满足同余就打印 `FAIL` 并以 1 退出。目录会递归，
  符号链接跳过（rootfs 里的链接是 guest 绝对路径，真实文件会被单独访问到）。
- `nr-tools embed` 现在**自带断言**：产物必须满足 16 KiB 同余，否则构建直接失败
  （和已有的 loader 指纹/glibc 版本断言同一风格）。断言读的是真正写出的文件。

## 运行期

`boot.rs` 不再假设 4096：`AT_PAGESZ`（auxv tag 6）在入口读一次存进 `KERNEL_PAGE`，
`page_size()` 优先用它，只有在 auxv 缺失时才退回 mprotect 探测。所有 `mprotect`
的取整都用它。
