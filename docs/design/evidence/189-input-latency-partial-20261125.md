# 189 · 触控/键盘延迟：这轮只拿到工具开销，端到端被两件事挡住

日期：2026-11-25 12:50–13:00（CST）。设备 RMX3357。目标（0.0.6 ④）：量化触控与键盘延迟。
结论先摆：**没有拿到可信的端到端数字**，拿到了一个分量数字和两个挡住测量的事实。不编数。

## 1 · 拿到的

`input` 工具自身的开销（device 侧 `date +%s%N` 包住命令，三次）：

| 命令 | 命令内耗时 |
|---|---:|
| `input tap 1200 540` | 36 ms |
| `input keyevent 66` | 35 ms |

FACT：这 35–36 ms 是 **Android `input` 工具的启动与投递开销**，跟 Husk 的运行时无关，
报端到端数字时必须单独列出来，否则会把工具开销算到环境头上。

整屏抓一次（`gl-probe-new2 root`）5 次：129 / 148 / 155 / 161 / 184 ms。
FACT：**靠轮询截图来量延迟，分辨率只有 ~150 ms**，量不了几十毫秒级的东西。所以
"输入 → 屏幕像素变化"这条最直观的量法在这台设备上不可用（除非改抓图路径）。

## 2 · 挡住测量的两件事

### 2.1 触控：注入的按下点不是手指点（evidence 185 的老问题）

`input tap 1700 700`（落在一个我们自己开的 `xev` 窗口正中）→ `xev` 一个 `ButtonPress` 都
没收到（`grep -c ButtonPress` = 0）。用 guest 内的 `xdotool mousemove 1700 700 click 1`
直接打 XTEST 也一样收不到。结合 185 的定位（2.0 侧 `ACTION_DOWN` 用的是上一次的光标位置，
不是手指点），当前会话里"点哪"和"点到了哪个窗口"对不上。

**FACT**：不先修 185 那个按下点语义，触控延迟没法在真机上年量出来——量的对象本身是错的。

### 2.2 键盘：我们的探针窗口拿不到焦点

`xev` 的窗口（`0x1c00001`）在 mutter 下 `X_SetInputFocus` 直接 `BadMatch`，`xdotool
getwindowfocus` 仍停在应用窗口（`0xe00004`）。所以 key event 只会进应用，不会进探针窗口。
反过来对**应用窗口**做 `windowfocus` 是成功的（`getwindowfocus` 立刻变成 `0xe00004`）。

**INFERENCE**：键盘这条链要量，得在应用里找一个"收到键就改状态"的可见信号。这一轮试过的
信号都不成立：`_NET_WM_NAME` 在只读文档上不随按键变化（`xprop -spy` 两分钟内零更新），
文档内容变化又只能靠像素判断——回到 §1 那 150 ms 的分辨率问题。

## 3 · 下一轮怎么量（方法已定，还没跑）

1. 应用侧要一个**便宜的可见信号**：用 `gnome-calculator` 敲数字，读 X 客户端自己的
   属性/标题（计算器会把结果放进窗口标题），或者用一个最小的 GTK4 探针程序——它把
   `key-pressed` 的时间写进 `_NET_WM_NAME`。后者最干净，但要先编。
2. X 侧基准用 XTEST 注入 + 探针窗口收事件的 **X 服务器时间戳差**（同一时钟，不需要换算），
   这样能把"Android 投递"和"X 侧处理"这两段分开。
3. 触控必须等 185 的按下点修完（那是 2.0 侧，不是运行时层能补的）。

## 4 · 口径提醒（发版时必须照这个写）

- 可以说：`input` 工具开销 35–36 ms、整屏抓图 129–184 ms、当前会话抓不到触控按下点。
- **不能**说：Husk 的触控/键盘延迟是 X ms——没测到。
