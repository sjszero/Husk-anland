# 187 · 窗口里"冒出尖尖"的机制：GTK4 的圆角裁剪层，钉默认渲染器即可消掉

日期：2026-11-25 12:40–12:50（CST）。设备 RMX3357（MT6893 / Mali-G77 MC9 / Android 13 /
4 KiB 页），应用 `com.linuxhub.myth.husk`。承接 evidence 186（窗口三角缺口定位到 GTK4 的 GL
路径），这一份把**是哪一层画的**和**修法**定死。

## 1 · 现象回想（186 的结论）

GTK4 客户端在 `GSK_RENDERER=ngl` + zink/PanVK 下，窗口里出现直边三角/菱形缺口；换
`llvmpipe` 或 `cairo` 干净；两帧逐字节一致。X 服务器、mutter 合成、path-shim 都已排除。

## 2 · 先扫驱动开关：都不是

固定 `GSK_RENDERER=ngl` + zink，逐个换 knobs，各起一次抓整屏：

| 配置 | 结果 |
|---|---|
| 默认 | 缺口 |
| `ZINK_DESCRIPTORS=lazy` | 缺口 |
| `MESA_GLES_VERSION_OVERRIDE=3.1` / `3.0` | 缺口 |
| `ZINK_DEBUG=flush` | 缺口 |

图：`187-zink-knob-sweep.png`。**INFERENCE**：不是描述符管理、不是 GL 版本上限、不是帧同步。

## 3 · 再二分"是哪个节点画的"：CSS 拆

GTK4 的 CSD 窗口自己画两样东西：窗口**阴影**（`box-shadow`，在窗口外面）和**圆角**
（`border-radius`，裁剪窗口本体）。用 `~/.config/gtk-4.0/gtk.css` 逐个关掉，数窗口体内
`(250,250,250)` 的像素（采样区域 x 180–900、y 30–560，步长 2；正常底板是 `(252,252,252)`）：

| CSS | 缺口像素 |
|---|---:|
| 都不关（基线） | 10 850 |
| 只关阴影 `box-shadow: none` | 9 219 |
| 只去圆角 `border-radius: 0` | **1 722** |
| 两个都关 | 1 218 |

**FACT**：缺口几乎全部由**圆角裁剪**这一层产生（8.6 倍），阴影本身基本无关（只降 15%）。

## 4 · 为什么看起来是"缺一块"而不是"多画了一块"

缺口里的颜色是 `(250,250,250)`——阴影层的内圈近白，**不是壁纸的蓝紫**（窗口右边界外才是
壁纸，取到 `(86,106,176)`）。也就是说：窗口本体该画的地方**没画上**，露出的是它下面已经画过
的阴影层，所以是"少画"，不是"画到外面去"。边是直边、并且是三角形/菱形，说明错在**图元级**
（三角形/四边形顶点），不是条纹、不是采样偏移。

**INFERENCE**（未证）：GTK4 的圆角裁剪走的是模板/掩码那一路，PanVK 这一层把它算错，
于是被裁掉的范围成了三角形；窗口底板因此少画一块，露出底色接近白的阴影层。

## 5 · 修法：GPU 不动，只钉 GTK4 的绘制后端

把默认值写进加载器那份 `/etc/husk/gpu-env`（安装器写）与 `/etc/profile.d/husk-gpu.sh`，
只加一行 `GSK_RENDERER=cairo`；程序自己设过的不覆盖。

用**发布版加载器**（`libld.so` = `d0153751ca94…`，与 0.0.5 包内一致）在同一棵树上起
`gnome-text-editor`，环境里**故意不设** `GSK_RENDERER`，靠加载器注入：

| 场景 | 缺口像素 |
|---|---:|
| 注入前（ngl） | 10 850 |
| 注入后（cairo） | **9** |

图：`187-before-ngl-zink.png` / `187-after-cairo.png`。**FACT**：加载器的 `getenv` 默认值
对 GTK4 真的生效（GTK 用 `g_getenv` 读 `GSK_RENDERER`）。

代价要写在这里：GTK4 应用的界面绘制吃 CPU（cairo）。Vulkan/GL 一点没动——mpv、glmark2、
Electron 这些自己开 GL 的程序仍然走 zink/PanVK。要让 GTK 重新吃 GPU：
`GSK_RENDERER=ngl` 覆盖即可，缺口会回来。

## 6 · 一个坑：这台设备现在跑着的会话用的不是发布版加载器

`ps` 里 gnome-shell 是 `libld-drmfd.so`（11-24 22:07 的实验构建），**早于** gpu-env 特性；
`libld.so` 是 11-25 11:44 的。所以在**当前这个手动会话**里注入不会生效，必须用发布版加载器
重开会话才看得到效果。正式会话（应用拉起的那条链）用的是发布版，这一点要在 0.0.6 的回归里
再确认一次。

## 7 · 顺手确认的两件事

- 背景/壁纸**可以**用 gsettings 改（把它改成纯品红验证过，桌面立刻变），所以 184 里漏掉的
  那半（背景默认值）确实能按同一套 override 补上，不是死路。
- `printenv` 看不到注入的变量（`environ` 里本来就没有，注入只回答 `getenv`），但 `gl-probe`
  与 GTK 都拿到了。谁是靠 `environ` 谁靠 `getenv`：**UNKNOWN**，不影响结论。

## 8 · 还没定的

PanVK 到底错在模板还是别的路径：**UNKNOWN**。下一步是一个最小复现——在 guest 里编一个
GLES2 程序（全屏三角 + 模板裁剪圆角矩形 + 回读），分别在 zink 与 llvmpipe 上跑，直接比像素。
这一步能证明/否掉"模板路径坏了"，也能拿去给 Mesa 报 bug。
