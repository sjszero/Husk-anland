# 228 · X11 呈现：除 DRI3 之外还有没有更便宜的交付路径

日期：2026-11-26 00:15（CST）。设备 UKHMMB8PYTGECMNV，桌面已启动（GNOME，2400×1080）。
这一份回答 0.0.13 审计里最后那个悬着的问题，先给结论：

**在当前布局里没有。** 更便宜的两条路（MIT-SHM、dma-buf/AHB 直传）都卡在同一件事上：
**X server 是应用里的 bionic 进程，不是 guest 进程**。它既用不了我们仿真的 SysV IPC，
也拿不到真 GPU 节点。要再往下走，得把 X server 搬进 guest，或者由应用侧把
X framebuffer 的拷贝换成 GPU 上传——两条都不在"改几行 shim"的量级。

---

## 1 · 现场事实（全部本机实测）

### 1.1 服务器是谁

```
$ run-as com.linuxhub.myth.husk cat /proc/17629/cmdline
com.linuxhub.myth.husk:x11
$ ... cat /proc/17629/maps | grep libc
/apex/com.android.runtime/lib64/bionic/libc.so      ← bionic
（maps 里没有 libld.so）
```

X server 跑在 `:x11` 进程里，链接的是 **bionic libc**，不经过 Husk loader。
`xdpyinfo`：X.Org 21.1.99，23 个扩展，其中 `DRI3`、`Present`、`MIT-SHM`、`GLX`、`DOUBLE-BUFFER`
都在。`xrandr`：`2400x1080 29.93*`。

### 1.2 MIT-SHM：服务器说有，但 attach 一定失败

```
XQueryExtension(MIT-SHM) = 1 (opcode=130)
XShmQueryVersion         = 1 -> 1.2 sharedPixmaps=1
XShmAttach               -> X Error: BadAccess (MIT-SHM minor 1)
```

guest 侧 SysV IPC 是**仿真**的（`shmget` 在这里的 Android 内核上直接 ENOSYS，shim 用
`/run/husk/ipc/shm/<id>` 文件 + `mmap(MAP_SHARED)` 重建，见 path-shim 的 §ipc 注释）。
guest 自测：`shmget`/`shmat`/`shmctl(IPC_STAT)` 全部正常，跨进程 attach 也正常
（child / exec 出去的 python 都能 `shmat`，`IPC_STAT` 报 `uid=0 cuid=0 mode=600 segsz=4096`），
`SO_PEERCRED` 也被改写成了虚拟 uid 0。

但 X server 是 bionic：它的 `shmget`/`shmat` 走的是**真内核**，而这个内核把 SysV IPC
编译掉了 → 服务器 attach 不了任何 segment → 回一个 `BadAccess`。
两边各说各话，MIT-SHM 在这套布局里**不可能通**。

后果不是"少一个扩展"，是每一个 X 客户端都退回 `XPutImage`。

### 1.3 客户端把一帧 2400×1080 推给 server 要多久

`xpresent`（libX11，`XPutImage` + 每帧 `XSync`，画面每帧都有真实 damage）：

| 分辨率 | 每帧 | 客户端 FPS | ms / 兆像素 |
|---|---|---|---|
| 2400×1080（2.592 MP） | 18.92 ms | 52.9 | 7.30 |
| 1600×720（1.152 MP） | 10.06 ms | 99.4 | 8.73 |
| 1280×720（0.922 MP） | 6.13 ms | 163.2 | 6.65 |
| 640×480（0.307 MP） | 2.60 ms | 385.1 | 8.47 |

像素线性、约 7–9 ms/兆像素：10.4 MB/帧 / 18.9 ms ≈ **550–660 MB/s**，就是一次协议拷贝的量级。
**一个客户端只是把桌面画出来，就已经吃掉 30 Hz 预算（33 ms）的一半以上。**

### 1.4 应用侧实际present了多少

应用自己的计数器（logcat，`LorieNative`），持续全屏动画 12 秒：

```
14 frames in 5.0 s = 2.8 FPS, 0/0 present copies offloaded to GPU
44 frames in 5.0 s = 8.8 FPS, 0/0 present copies offloaded to GPU
47 frames in 5.0 s = 9.4 FPS, 0/0 present copies offloaded to GPU
28 frames in 5.0 s = 5.6 FPS, 0/0 present copies offloaded to GPU
```

两件事：
- **5–9 FPS**。客户端那边能推 53 FPS，屏幕这边 5–9 FPS，瓶颈在应用侧。
- **`0/0 present copies offloaded to GPU`**：那条"交给 GPU"的路径一次都没走到。

（`choreographer=301 redraw=301 wait=0`：应用的 Android 帧循环本身是满 60 Hz 且不等 vsync，
所以不是被 Android 的 vsync 卡住的。）

### 1.5 GPU 节点

guest 里 `/dev/dri` 是 shim 合成的：`card0` 显示 `10,33`，`renderD128` 的 stat 是
`d?????????`。`open()` 这两个节点会拿到 fd（合成层给的），但**不是真 DRM 节点**。
所以 DRI3 即使服务器支持、客户端也拿到 fd，后面每一个 ioctl 都落不到 Mali 上。

## 2 · 三条交付路径，各自卡在哪

| 路径 | 省掉什么 | 现在为什么不行 | 要动哪一层 |
|---|---|---|---|
| **DRI3 + dma-buf** | 客户端→server 的整次像素拷贝 | 应用域打不开真 render 节点（`renderD128` 在本机就不存在，`card0` 是 0660 system:system）；guest 里的是合成 fd | 设备/权限，或让 server 用 AHB 而不是 DRM 节点 |
| **MIT-SHM** | 客户端→server 的协议拷贝（只传一段小请求） | server 是 bionic，SysV IPC 走真内核 → ENOSYS → `BadAccess` | X server 换成 guest 内运行（走 shim 的仿真 IPC） |
| **应用侧 GPU 上传** | server→surface 的 CPU 回读/拷贝 | 应用侧的 `present copies offloaded to GPU` 计数是 `0/0`，这条路径没启用 | 应用侧（2.0 的呈现代码） |

## 3 · 结论与建议（按代价从低到高）

1. **最便宜的下一步在应用侧**：X framebuffer 已经从 server 读回来了，把"读回来 → CPU 拷进
   共享内存 → 上传"换成"读回来 → 直接当纹理上传/合成"。这不需要动 server，也不需要 DRI3。
   判据就是那个计数器：`present copies offloaded to GPU` 从 `0/0` 变成 `N/N`，
   同时 5–9 FPS 应该上去。
2. **真正的零拷贝要把 X server 搬进 guest**：guest Xorg（glibc、走 shim）渲染到
   `/run/husk/ipc/shm` 的段或应用传进来的 AHB fd，应用直接 mmap 同一块内存 / 同一个
   AHB 去 present。这时 MIT-SHM 自动可用（客户端和 server 都在 guest、都走仿真 IPC），
   应用侧也不用再读回。代价是换 server，属于 0.0.14 之后的架构题。
3. **DRI3 不值得等**：这台机型在应用域里就没有 render 节点；换机型也解决不了
   "server 和应用不在同一权限域"的问题。
