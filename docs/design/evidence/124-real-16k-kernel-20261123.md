# 124 · 第一次在**真的 16 KiB 内核**上跑我们的 loader：两个真 Bug

日期：2026-11-23　宿主：macOS x86_64 + QEMU 11.0.3（TCG）
被测物：`tools/loader/ld-embedded.so`（loader + shim v3.x）、打过槽位的 `libc.so.6`、Ubuntu 24.04 base rootfs
全部结论来自本机实测；没有 16K 真机，所以这里是"虚拟硬件 + 真 16K 内核"，不是骁龙真机。

## 1. 环境怎么造的（可复现）

公开资料里没有任何高通 16K 内核（见 `husk-notes/prior-art/page-size-public-20261123.md`），
但**公开的 16K 内核有**：Raspberry Pi 5 的 `kernel_2712.img` 就是 16K 页内核。

```sh
curl -LO https://github.com/raspberrypi/firmware/raw/master/boot/kernel_2712.img
gzip -dc kernel_2712.img > Image.rpi5
file Image.rpi5     # → Linux kernel ARM64 boot executable Image, little-endian, 16K pages

# initramfs = Ubuntu 24.04 base rootfs + 我们的 loader + 打过槽位的 libc
(cd root && find . | cpio -o -H newc | gzip -1 > initramfs.cpio.gz)

qemu-system-aarch64 -M virt -cpu max -smp 4 -m 3072 -nographic \
  -kernel Image.rpi5 -initrd initramfs.cpio.gz \
  -append "console=ttyAMA0 rdinit=/init loglevel=6 panic=1" -no-reboot
```

进 guest 后（FACT）：

| 检查 | 结果 |
|---|---|
| `uname -r` | `6.18.64-v8-16k+` |
| `/proc/self/auxv` 的 `AT_PAGESZ` | `0x4000` = **16384** |
| 原厂 `lib/ld-linux-aarch64.so.1` + `usr/bin/getconf PAGESIZE` | **16384**，rc=0 |
| 原厂 loader + `usr/bin/bash -c ...` | 正常（Ubuntu noble 的 ELF 本来就是 64K 对齐） |

⇒ 这个环境是真的 16K 内核，可以当判据用。**原厂 glibc 在这套环境里是好的，所以后面所有崩溃都是我们的。**

## 2. Bug A：shim 段和 loader 自己的段在 16K 上共用同一个页（已修）

现象（FACT，`strace` 记录）：

```
execve("./libld.so", ...) = 0
--- SIGSEGV {si_signo=SIGSEGV, si_code=SEGV_ACCERR, si_addr=0x7fff809d0b48} ---
+++ killed by SIGSEGV +++
```

execve 之后**一条 syscall 都没有**就死了——连我们自己 hook 里的 `mprotect` 都没跑到，
说明死因在 ld.so 自己的启动阶段，与 shim 的代码无关。

根因（FACT，由 phdr 直接算出）：内核按**自己的**页大小映射每个 `PT_LOAD`：

```
原 loader 最后一段:  vaddr=0x3e988 memsz=0x29c0  → 结束于 0x41348
我们加的 shim 段:    vaddr=0x42000（F_BASE+SEG_ALIGN）
```

| 内核页 | loader 末段实际映射区间 | shim 段实际映射起点 | 结果 |
|---|---|---|---|
| 4 KiB | `0x3e000…0x42000` | `0x42000` | 不重叠，正常 |
| 16 KiB | `0x3c000…0x44000` | `0x40000` | **重叠 16 KiB**，shim 用 MAP_FIXED 覆盖了 loader 的 .data/.got 尾部 |

这就是 4K 设备一直好用、16K 上必死的原因。

修法（`runtime/crates/nr-tools/src/main.rs`）：`V_BASE` 从 `0x42000` 改成 **`0x52000`**
（= `ALIGN(LD_TEXT_END, 0x10000) + F_BASE % 0x10000`），并把重叠判据从 `PAGE`(4K) 改成
`SEG_ALIGN`(64K)； congruence 判据同样改成 64K，保证 p_offset ≡ p_vaddr (mod 64K)。

验证：修完后同一套环境里 `./libld.so --list` 不再崩，能正常报出库列表（FACT）。

## 3. Bug B：hook 的 mprotect 用的是 4 KiB 对齐（已修到"内核接受"，还有下一层）

现象（FACT）：hook 里 `mprotect` 4K 对齐 → 16K 内核回 `EINVAL`；返回码被忽略 →
shim 的 .data/.bss 仍然是只读 → 第一次写自己的静态变量就 SIGSEGV。

修法（`tools/loader/init-hook.S`）：不再假定 4 KiB，按 4K → 16K → 64K 依次尝试，
第一个内核接受的即为真实页大小；三次都失败则打印
`nr-hook: mprotect of the shim's writable segment failed at 4K, 16K and 64K` 并 `exit_group(98)`，
绝不带着只读对象继续 interpose。

验证（FACT，strace）：

```
mprotect(0x7fff5698a000, 73728, PROT_READ|PROT_WRITE) = -1 EINVAL
mprotect(0x7fff56988000, 81920, PROT_READ|PROT_WRITE) = 0
```

4K 尝试被拒、16K 尝试被接受——页面大小自适应生效。

## 4. 还没解决的（UNKNOWN，下一步）

同一次运行里，紧接着那次成功的 mprotect 之后仍然死：

```
mprotect(0x7fff56988000, 81920, PROT_READ|PROT_WRITE) = 0
--- SIGSEGV {si_signo=SIGSEGV, si_code=SEGV_ACCERR, si_addr=0x7fff56988000} ---
```

`si_addr` 正好是刚设成可写的窗口起点，`SEGV_ACCERR` 表示"有映射但没权限"。
说明窗口里有一个页并不是我们以为的那一页（或者窗口跨进了 glibc 自己的 `PROT_NONE` 保护区）。
下一步按 `strace` 里的窗口地址和 `rw_start/rw_len` 逐页核对 `/proc/self/maps`。
