WHY THIS TOOK MORE THAN "EMBED THE SHIM" (FACT, each item was a stopping point)
Interposing open/stat/execve is not enough, because a lot of libc's *own* code does
not go through the PLT: it calls internal aliases such as __open64_nocancel, which no
GOT patch can see. Every failure below was diagnosed from the device, not guessed:

  1. gcc's first temp file: "Cannot create temporary file in /tmp/: Permission denied"
     mkstemps() generates the name in __gen_tempname() and creates it with an internal
     open. The guest path "/tmp/ccXXXXXX" therefore reached the kernel verbatim and hit
     the *host's* /tmp, which on this ROM is shell-owned mode 0771 -> EACCES.
     -> the shim now implements mkstemp/mkstemps/mkostemp/mkostemps/mkdtemp itself:
        random six characters from auxv AT_RANDOM (getrandom(2) is trapped by this
        ROM's seccomp policy: it kills the process with SIGSYS) + O_EXCL through our
        own resolver, so the caller's template stays a guest path.

  2. "cannot execute 'cc1': execvp: No such file or directory"
     gcc builds its whole program search path from /proc/self/exe, so it asks the
     kernel for paths that are *already real* (<root>/usr/libexec/...). Mapping those
     again produced <root><root>/usr/... -> ENOENT. It also calls execv()/execvp(),
     which are libc internals.
     -> anything under the root is now taken verbatim (under_root()), and execv,
        execvpe, execvp are interposed (PATH search redone on guest paths).

  3. "Bad system call" (SIGSYS) from cc1
     libc's realpath() calls faccessat(), whose first attempt is faccessat2 - a syscall
     this ROM's policy answers with SIGSYS instead of ENOSYS. The trap log named the
     frame: pc inside faccessat+76, caller return address decoded to realpath+0x608.
     -> realpath/__realpath_chk/canonicalize_file_name are interposed, which both
        removes the trap and makes realpath() return a *guest* path.

  4. as(1) "can't create /tmp/ccXXXXX.o: Permission denied"
     as does not import open() at all: it opens its output with fopen(), whose internal
     alias bypassed us.
     -> fopen/fopen64/creat/creat64 are interposed as open()+fdopen().

  5. ld.bfd "error loading plugin ... cannot open shared object file"
     collect2 loads the LTO plugin with dlopen() of an absolute guest path.
     -> dlopen() is interposed and calls dlmopen(LM_ID_BASE, ...) internally. Our own
        object is not in the link map, so "the real dlopen" is simply dlmopen with the
        base namespace, which is the same function under another name.

  6. make: "gcc: No such file or directory" even though POSIX names were interposed
     make does not call execve: it calls find_in_given_path() -> eaccess() ->
     posix_spawn(). glibc's eaccess short-circuits to the internal access() when the
     real and effective ids match, and posix_spawn execs through an internal execve, so
     a translated path would still have arrived without its interpreter.
     -> eaccess/euidaccess are interposed, and posix_spawn/posix_spawnp are implemented
        here: fork, honour the attribute getters, apply the file actions, then exec
        through our own execve. The opaque file-actions layout was dumped on the device
        first (32-byte entries: tag +0, fd +8, new_fd +12, path +16, oflag +24,
        mode +28; header {int allocated; int used; entry *actions}), and the parser
        rejects anything that does not look like that.

  7. ls -l "cannot read symbolic link": ls imports __readlink_chk, not readlink
     Ubuntu is built with _FORTIFY_SOURCE=3, so plain calls become __*_chk wrappers,
     which are separate exported symbols resolved to libc's own code.
     -> __readlink_chk, __readlinkat_chk, __open_2, __open64_2, __openat_2,
        __openat64_2, plus the *64 twins (stat64/lstat64/fstatat64/fstat64) and
        faccessat(), which dash(1) uses for its PATH search.

Nothing above is interception at run time: it is a wider set of entry points in the
same single Rust object, still with zero syscall supervision.

NOT DONE / KNOWN LIMITS (UNKNOWN unless stated)
  * posix_spawn here uses fork(), not glibc's vfork/clone path. make is fine; a
    multithreaded caller would pay a page-table copy.
  * freopen, dlmopen, glob, nftw, posix_spawn_file_actions_addopen of a *guest* path
    inside a library that libc applies itself: not exercised yet.
  * g++ / libstdc++ are not provisioned, so C++ is untested.
  * the guest still inherits the app's TMPDIR (an absolute host path), which resolves
    inside the guest root and does not exist. gcc happens to use /tmp; other tools
    would need the launcher to set TMPDIR=/tmp.

CORRECTION (2026-11-22, see evidence/20)
  Item 1 above says getrandom(2) "is trapped by this ROM's seccomp policy: it kills the
  process with SIGSYS". Measured later in the same domain: getrandom() returns data
  (8 bytes, errno 0). The temp-name code still uses auxv AT_RANDOM - that is the better
  design either way - but this particular justification was wrong.
