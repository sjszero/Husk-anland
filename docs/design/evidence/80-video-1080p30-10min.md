# Evidence 80 — 1080p30 H.264 硬解连续 10 分钟门禁

日期：2026-11-23
设备：RMX3357 / MT6893 / Mali-G77 MC9 / Android 13 / kernel 4.19.191 / 4 KiB / arm64
运行域：`untrusted_app`（`com.linuxhub.husk`）
rootfs：`/data/user/0/com.linuxhub.husk/files/rootfs-full`
测试源：`ffmpeg testsrc2` 合成彩条，1920x1080 / 30 fps / 600.000 秒 / 18,000 视频帧

## 结论

**FACT — H.264 10 分钟门禁通过。** 真实 `c2.mtk.avc.decoder` 接收 18,000 个压缩
sample，输出 18,000 个视频帧，显式 `dropped=0`；guest 侧完成 18,000/18,000 次
YV12→RGBA8 GPU 转换和 AHB 回交，app 侧提交 18,000/18,000 次 SurfaceControl 上屏，
`present_fail=0`。桥接发送耗时 **600.097 秒**，guest 统计吞吐 **30.03 fps**。

```text
bridge: EOS_OK frames=18001 images=18001 expected=18000 decoded=18000 dropped=0
bridge: guest|DONE|samples=18000|bytes=300604636|elapsed_ms=600097
guest:  expected=18000|completed=18000|dropped=0|elapsed_ms=599462|fps=30.03
app:    sent=18000|completed=18000|presented=18000
app:    pipeline_dropped=0|present_dropped=0|present_fail=0
app:    handles=6|reuses=17994
```

这里的 `frames=18001 / images=18001` 包含 MediaCodec 的 EOS output buffer；实际视频帧数是
`18001 - 1 = 18000`，桥接日志同时写明了 `expected=18000|decoded=18000`。

截图证明这不是“只 ACK 未显示”：测试跑到约 10 分钟时，画面仍显示 `testsrc2` 彩条和
`00:09:59.966` 时间码。静态图见
[`80-video-1080p30-10min-end.png`](80-video-1080p30-10min-end.png)。

## 链路与判定口径

- guest 解复用 MP4，压缩 AVC access unit 经共享内存 ring 交给 app。
- app 内纯 Rust 代码通过 NDK `AMediaCodec` 调真实 `c2.mtk.avc.decoder`。
- MediaCodec ByteBuffer 输出复制进 6 个应用持有的固定 YV12 AHardwareBuffer。
- 每个固定 slot 的 dma-buf 在 guest PanVK 中导入，持久 compute converter 执行
  YV12→RGBA8，结果写入同一 slot 对应的 RGBA8 AHB。
- app 把 RGBA8 AHB 经 SurfaceControl 交给 SurfaceFlinger。
- `dropped` 是显式的 `expected - completed` / `expected - decoded`，不是用耗时阈值冒充。
  日志中的 `slow_gt_33ms` 统计的是“等待下一帧 + 处理”的总间隔，包含实时播放的 33.3 ms
  节拍，因此不能拿它计算丢帧；本证据的丢帧判定只使用 `dropped`。

## 上屏完成与资源

**FACT**：SurfaceControl 的提交计数在 EOS 时已经达到 18,000；完成计数当时还有 3 帧在
SurfaceFlinger 管线中。后续排空到：

```text
video|present|clear|submitted=18000|completed=18000|released=18000
```

因此 app 日志里的 `presented=18000` 表示 18,000 次提交，而最终 `present|clear` 证明
18,000 次提交全部完成并释放。

资源采样使用 app PID 的 `/proc/<pid>/status` 和 `/proc/<pid>/fd`：

| 阶段 | VmRSS | Threads | fds |
|---|---:|---:|---:|
| 会话前基线 | 151,880 KiB | 40 | 134 |
| 长测峰值 | 205,616 KiB | 47 | 249 |
| 长测结束后稳定值 | 203,300–204,020 KiB | 44 | 136 |
| 再跑 150 帧后 | 203,300 KiB | 44 | 136 |

**FACT**：fd 和线程在第二次 150 帧会话后没有继续增长，说明没有逐会话泄漏。
**FACT**：会话后没有回到启动前的精确基线，RSS 多保留约 51 MiB，fd 多 2 个，线程多 4 个。
保留原因目前是 **UNKNOWN**，不能写成“所有资源完全回到基线”；但已完成 600 秒长测和
第二次会话对照，未观察到持续增长。

## 验证覆盖

- `video-verify-every=900`：前 6 帧覆盖全部 6 个 slot；之后每 900 帧做一次 CPU plane
  hash + GPU 三平面回读 + YUV 采样点校验。
- guest 汇总：6 个 slot 合计 18,000/18,000 次 GPU 转换成功，converter failures=0。
- 因为 900 是 6 的倍数，周期性校验都落在 slot 0（20 次），其余 slot 各在前 6 帧校验
  1 次；所有 slot 的每一帧仍执行真实 GPU 转换。后续更均匀的周期校验应使用与 slot 数
  互质的间隔（例如 901）。

## 边界：不能误写成整条视频完成

**FACT**：MediaCodec 仍是 ByteBuffer → CPU I420/YV12 拷贝，不是 decoder→GPU 零拷贝。
本证据完成的是“硬件解码 → 固定 AHB → PanVK YUV 转换 → SurfaceControl 实时上屏”的
H.264 长时间门禁。

**仍未完成**：HEVC / VP9 / AV1 门禁、decoder→GPU 零拷贝、guest WSI/swapchain、
GStreamer/VA-API、Chromium `<video>`、GNOME 播放器、AV 同步 `<40ms`、硬解 vs 软解
CPU 对比、跨芯片降级真机验证，以及 LinuxHub 2.0 proot 替换。

## 复现

生成测试源：

```sh
ffmpeg -hide_banner -y -f lavfi -i 'testsrc2=size=1920x1080:rate=30' \
  -frames:v 18000 -an -c:v libx264 -preset ultrafast -tune zerolatency \
  -profile:v main -pix_fmt yuv420p -g 60 -keyint_min 60 -sc_threshold 0 \
  -b:v 4M -maxrate 4M -bufsize 8M -movflags +faststart \
  /tmp/husk-video/avc-1080p30-600s.mp4
```

构建与部署：

```sh
cd app-rs
NDK=$NDK
CARGO_TARGET_AARCH64_LINUX_ANDROID_LINKER=$NDK/aarch64-linux-android24-clang \
  cargo build --release --target aarch64-linux-android
cp target/aarch64-linux-android/release/libhuskapp.so \
  ../app/app/src/main/jniLibs/arm64-v8a/libhuskapp.so
cd ../app && ./gradlew :app:assembleDebug

cd ../runtime
CARGO_TARGET_AARCH64_UNKNOWN_LINUX_GNU_LINKER=$NDK/clang \
RUSTFLAGS='-C link-arg=--target=aarch64-linux-gnu -C link-arg=--sysroot=/tmp/gccroot -C link-arg=-fuse-ld=lld' \
  cargo build --release -p vulkan-probe -p video-bridge \
  --target aarch64-unknown-linux-gnu
```

设备侧 marker 与启动顺序：设置 `files/video-bridge`、`files/video-ahb`、
`files/video-fixed`、`files/rootfs-full/run/husk/present` 和
`files/video-verify-every=900`；启动 NativeActivity 后，先启动 guest
`vulkan-probe-verify --video-ahb-frames 18000 --video-verify-every 900`，再启动：

```sh
HUSK_VIDEO_REALTIME=1 video-bridge \
  /run/husk/video.sock /tmp/husk-video/avc-1080p30-600s.mp4 18000
```
