LinuxHub Husk - evidence 22: the build tools are Rust now, byte for byte
Date: 2026-11-22   Host: macOS aarch64   Target of the product: PLE110 / Android 16 / 6.6.118
Task: take the ELF surgery out of Python, with byte identity as the acceptance test.

WHY
  The loader is a patched glibc binary; whoever builds it must be able to prove the
  patch is exactly what was verified. Two implementations of that surgery (Python and
  Rust) that agree to the byte are worth more than either one alone: the Rust one can
  live in the workspace, share types with the shim, and drop the python3 requirement;
  the Python one stays as the oracle.

WHAT WAS PORTED (crates/nr-tools, no dependencies)
  nr-tools scan-syscalls report <elf> [--version V] [--expect NAME=COUNT ...]
  nr-tools scan-syscalls patch  <elf> <out> [...]     <- nr-scan-syscalls.py
  nr-tools embed <shim.so> <loader.orig> <hook.bin> <out.so>   <- nr-embed.py
  Every assertion, message and exit code of the originals is preserved, because a
  refusal is part of the contract (a different glibc must fail loudly).

TWO BUGS THE PORT FOUND (both in the port, not in the shipped loader)
  * NOT_INTERPOSED had drifted: the Rust copy carried two names that no longer exist
    ("nr_execv_v", "nr_execvp_v", left over from an abandoned experiment) and had lost
    "bcmp". Result: 77 interposed names instead of 76, one extra table entry, a
    different descriptor address and a loader one page shorter. Fixed by diffing
    against the Python constant rather than from memory.
  * align() in nr-embed.py defaults to PAGE, not to 8: the hook is padded to a whole
    page before the tables (hook 288 B -> 4096 B). The port initially padded to 8,
    which moved descriptor_vaddr by 3808 bytes. Fixed, with a comment.
  Both were caught by the byte comparison, which is exactly why the acceptance test is
  bytes and not "it looks right".

REMAINING (deliberately not done in this pass)
