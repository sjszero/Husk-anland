# evidence 162 — 整块 `glReadPixels` 只写第一行+第一列（FACT，两个驱动都一样）

设备/安装/时间同 evidence 161。探针：最小绘制程序 + 两种驱动对照。

## 1. 现象（FACT）

把 16×16 的 FBO 附件**清成纯红**（不画任何几何），然后整块读回：

```
预填 0xAA 后：未写入=225 红=31 全零=0 其它=0
读 1x1  -> 红 1/1
读 2x2  -> 红 3/4
读 4x4  -> 红 7/16
读 8x8  -> 红 15/64
读 16x16 -> 红 31/256
单点 (8,8) = 255,0,0,255
```

- 写入的像素数正好是 `2N−1`：**第一行 + 第一列**，其余一个字节都没动（预填 0xAA 可证）。
- 32×32 同样：63/1024。
- **1×1 读任意坐标都正确**（`(8,8)` 拿到该点真值）。
- `glGetError()` 全程 0；FBO status `0x8CD5`（完整）。
- **`GALLIUM_DRIVER=llvmpipe` 与 zink 完全一致** → 与 Mali/PanVK 无关，也不是 GPU 侧问题；
  它在 Mesa 的读回（pack/transfer）这一层，或更下面。

## 2. 影响

- 任何「截图 = 整块 `glReadPixels`」的工具（截图、录屏、像素比对脚本）在这棵树上都会拿到
  基本全零的画面，而且**不报错**——这正是最容易把「驱动读回缺陷」误判成「渲染没出来」的坑。
  2026-11-24 我自己的 ES3 探针就先踩了一次。
- 规避：探针一律逐像素 1×1 读（`tools/device-tests/es3-workload.c` 就是这么写的），
  或者走 dma-buf / `AHardwareBuffer` 那条导出链（另一条路，未在本轮验证）。
- 候选原因（**UNKNOWN**，未定）：读回走 `u_transfer` 时行距/尺寸被算错，或这台设备的
  `PACK_ALIGNMENT`/行拷贝在某个上限被截断。要定位需要这版 Mesa 的源码与一次 gdb 断点，
  本轮没做；先把它当**已知缺陷**写进文档，别在别处再踩。
