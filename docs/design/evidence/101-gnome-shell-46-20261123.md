（含 evidence 100 的 `nr_repatch`）

## 1 之前卡在哪

evidence 99 的记录是：GTK 客户端半路 bail（`gdk_set_allowed_backends` 找不到、
pixbuf 认不出格式）。本次把这两条拆开验证，得到的结论：

| 症状 | 归因 | 结论 |
|---|---|---|
| `Could not locate gdk_set_allowed_backends: liblzo2.so.2: cannot open shared object file` | rootfs 缺 `liblzo2-2`，且 `--library-path` **替换**了 loader 的默认搜索路径，把 `lib/aarch64-linux-gnu` 排除在外 | FACT，已修 |
| `Failed to load module: .../gio/modules/libgvfsdbus.so`（`libgvfscommon.so` 找不到） | rootfs 缺 `gvfs-libs`；libgvfscommon 不带版本后缀、放在 `usr/lib/aarch64-linux-gnu/gvfs/` | FACT，已修 |
| pixbuf *Couldn't recognize the image file format* | 见 evidence 100 §3.1：宿主绝对路径同样失败 + 没有 `loaders.cache` ⇒ **不是**路径层 | FACT（归因纠正） |

修法（都只是把缺失的东西补进 rootfs，属打包，不是改运行时）：

```sh
# 从 2.0 的离线包（只读）里取 .deb，按 data.tar 解到 rootfs
tar xf offline/gnome-24.04-arm64.tar -C /tmp/gnomepkg --strip-components 1 \
    ./packages/liblzo2-2_2.10-2build4_arm64.deb \
    ./packages/gvfs-libs_1.54.4-0ubuntu1~24.04.5_arm64.deb \
    ./packages/gvfs-common_1.54.4-0ubuntu1~24.04.5_all.deb \
    ./packages/libgdk-pixbuf2.0-common_2.42.10+dfsg-3ubuntu3.3_all.deb \
    ./packages/libgdk-pixbuf-2.0-0_2.42.10+dfsg-3ubuntu3.3_arm64.deb
# ar + data.tar.{xz,zst} 解到 /tmp/gnomeroot1 → tar czf → 推设备 → 解到 rootfs-full
```

`tools/device-tests/gexec.sh` 的库路径（`--library-path` 是**替换**不是追加）：

```
$R/lib/aarch64-linux-gnu:$R/usr/lib/aarch64-linux-gnu:
$R/usr/lib/aarch64-linux-gnu/mutter-14:$R/usr/lib/gnome-shell:
$R/usr/lib/aarch64-linux-gnu/gvfs
```

## 2 结果（FACT）

```
$ sh gexec3.sh rootfs-full usr/bin/gnome-shell --headless --no-x11
libmutter-Message: Running GNOME Shell (using mutter 46.2) as a Wayland display server
libmutter-Message: Using Wayland display name 'wayland-0'
```

- 进程存活 25 s（`timeout -s KILL` 杀掉，exit 137），不是退出；
- `$XDG_RUNTIME_DIR/wayland-0` socket 建立并可连（自写的 15 行 C 客户端 `connect()` 成功）；
- JS 初始化不再抛异常（之前是 `Module .../ui/init.js threw an exception`，直接 exit 1）；
- GTK4 客户端 `gnome-text-editor` 在 `WAYLAND_DISPLAY=wayland-0` 下连续运行 10~12 s，
  **没有任何 GTK/显示错误**（之前是 `Gtk-WARNING: Failed to open display`），被 timeout 杀掉；
- `gnome-shell-calendar-server`、at-spi2 的 bus 等子进程被正常拉起。

其余日志（都是**已知缺服务**，不是运行时问题）：RTKit 不存在、colord 不存在、
`org.gnome.SessionManager` 不存在（没有 session manager）。

## 3 dbus：能通，但别用 `--fork`（FACT + 一条教训）

单个 `dbus-daemon --session --nofork --address=unix:path=$XDG_RUNTIME_DIR/bus` 时：

```
$ gdbus call --session --dest org.freedesktop.DBus ... ListNames
(['org.freedesktop.DBus', ':1.0'],)
```

用 `--fork` 时本机出现**同一 address 上多个 dbus-daemon**（一次实测 3~4 个：
`do_wait` 的父进程 + 两个在 `ppoll` 的子进程），此后所有客户端（`gdbus`）连上去
**读不到回应**、10 s 后被杀（rc=137）。原因未查清（UNKNOWN），但结论已够用：
启动脚本必须 (1) 先精确清掉旧 daemon，(2) 用 `--nofork` 自己后台化，(3) 目录
`chmod 700`（dbus 拒绝 world-writable 的 `XDG_RUNTIME_DIR`，会报
`Unable to set up transient service directory`）。

## 4 仍未验证（UNKNOWN，别当成完成）

- **窗口是否真的上屏**：两次尝试 `org.gnome.Shell.Screenshot.Screenshot` 都因 dbus
  卡住而超时，没拿到 `shot.png`。所以「客户端连上了合成器」是 FACT，
  「窗口被 map / 有帧」是 UNKNOWN。
- GNOME Shell 的帧仍然只能到 `--headless` 的 surfaceless 渲染器（`Created surfaceless
  renderer without GPU`），接 ScreenCast → dma-buf → AHB → SurfaceControl 还是下一步。

## 5 复现

```sh
F=/data/data/com.linuxhub.husk/files; R=$F/rootfs-full
export XDG_RUNTIME_DIR=$R/tmp/xdg7; mkdir -p $XDG_RUNTIME_DIR; chmod 700 $XDG_RUNTIME_DIR
export DBUS_SESSION_BUS_ADDRESS=unix:path=$XDG_RUNTIME_DIR/bus
export MESA_LOADER_DRIVER_OVERRIDE=zink GALLIUM_DRIVER=zink
export VK_ICD_FILENAMES=$R/usr/share/vulkan/icd.d/husk_panvk_frist370_execva.json
export __EGL_VENDOR_LIBRARY_FILENAMES=$R/usr/share/glvnd/egl_vendor.d/50_mesa.json
export XKB_CONFIG_ROOT=$R/usr/share/X11/xkb
cd $F
nohup sh -c "exec sh gexec3.sh rootfs-full usr/bin/dbus-daemon --session --nofork --address=unix:path=$XDG_RUNTIME_DIR/bus" &
nohup sh -c "exec sh gexec3.sh rootfs-full usr/bin/gnome-shell --headless --no-x11" &
sleep 15
WAYLAND_DISPLAY=wayland-0 sh gexec3.sh rootfs-full usr/bin/gnome-text-editor
```
