# 154 · 「完整 Linux 环境」实测挖出的四个 bug：apt 装不了包、ldconfig、libc 补丁被覆盖（FACT）

日期 2026-11-24 15:20–15:45 · RMX3357（MT6893 / Android 13 / kernel 4.19.191 / 4 KiB / arm64）
包 `com.linuxhub.myth.husk`（debug），`untrusted_app`，LinuxHub 2.0 rev 22

起点是一个简单问题：「能不能 `apt install` 装东西」。答案是**不能**，而且不是一个 bug，
是一串：装包失败 → 修掉 → 装成功了 → 装成功本身又踩坏了运行时。

## 0 · 四个 bug 与结论

| # | 现象 | 根因 | 修在哪 | 修完实测 |
|---|---|---|---|---|
| 1 | `apt-get install` 报 `E: Couldn't determine free space in /var/cache/apt/archives/ - statvfs (2: No such file or directory)` | `statvfs(3)` 是 glibc 内部对 `statfs(2)` 的包装，它的路径**不经过 GOT**，shim 没有这个符号 → 内核拿 host 路径去 statvfs | shim 新增 `statvfs` / `statvfs64`：翻译一次路径 + `statfs` 系统调用 + glibc 的字段映射 | `os.statvfs('/')` 从 host 的 194 478 块变成 guest 的 28 292 600 块；`os.statvfs('/var/cache/apt/archives')` 不再 ENOENT |
| 2 | `dpkg --configure libc-bin` 失败：`/sbin/ldconfig.real: Can't stat /lib`、`Can't create temporary cache file /etc/ld.so.cache~: Read-only file system` | Ubuntu 的 `ldconfig.real` 是**静态** PIE：没有动态符号，shim 无从插手，它把 `/lib`、`/etc` 解析到 Android host 命名空间 | 装 `husk-ldconfig`（guest 自己的 cache writer），`/sbin/ldconfig.real` 换成转发脚本，原静态二进制留作 `ldconfig.real.glbc` | `ldconfig` rc=0、`wrote /etc/ld.so.cache (950 entries from 6 directories)`；`dpkg --configure -a` rc=0，815 包全部 `ii` |
| 3 | （1、2 修完后）`apt install build-essential git vim nodejs ...` 成功 | — | — | 27 秒装完，包数 815 → **882**，`gcc/make/git/vim/node` 全部可选；`apt install` 从此可用 |
| 4 | 装完包后**桌面起不来**：`/bin/sh: 1: Cannot fork`，`ensureSudoInstalled` 抛 `IllegalStateException` | `apt` 把 libc6 从 `2.39-0ubuntu8.7` 升到 `8.12`，**覆盖了运行时打过补丁的 libc**。补丁有两处：libc 内部调用的 slot 页、`clone3 → ENOSYS`。丢了之后 `getent shadow` 返回空（nss_files 在 libc 里直接 `fopen` host 的 `/etc/shadow`），2.0 的 sudo 修复脚本 `exit 1`，会话脚本随之失败 | 用 `nr-tools libc-interpose` + `scan-syscalls patch` 对 8.12 重新打补丁；`tools/guest-config/install-libc-patch.sh` 把这条链固化成脚本 | `getspnam("husk")` 从 NULL/ENOENT 变成 found（hash 106 字节）、`getent shadow husk` 非空；桌面起来（15:45 截图，GNOME 46 X11，882 包 rootfs） |

## 1 · bug 1：statvfs 不在 shim 的符号表里（FACT）

复现（guest 内，Python 三行）：

```
$ python3 -c "import os;print(os.statvfs('/').f_blocks)"
194478                      # ← Android /data 的块数，不是 guest rootfs 的
$ python3 -c "import os;print(os.statvfs('/var/cache/apt/archives').f_blocks)"
FileNotFoundError: [Errno 2] No such file or directory: '/var/cache/apt/archives'
```

同一个路径 `ls -ld` 明明存在：

```
$ ls -ld /var/cache/apt/archives
drwxr-xr-x 3 root root 20480 /var/cache/apt/archives
```

所以不是路径解析，是**这条调用根本没被改写过**。修完以后：

```
$ python3 -c "import os;print(os.statvfs('/').f_blocks, os.statvfs('/var/cache/apt/archives').f_bavail)"
28292600 8321063
```

修法：`runtime/crates/path-shim/src/lib.rs` 新增两个导出符号（`statvfs`、`statvfs64`），
实现是「`xattr_pinned` 翻译路径 → `statfs(2)` → glibc 的 statfs→statvfs 字段映射」。
重建后的 loader：`sha256 85b65ca4cde23dd7762e93b54bcac0e76f3623424d3b8c4e32078c01780c1444`，
`embed` 报 `interposed 171 → 173`，`assets.version = husk-runtime-spawn-link-22`。

## 2 · bug 2：静态 ldconfig 天生看不见 guest（FACT）

```
$ ldconfig
/sbin/ldconfig.real: Can't create temporary cache file /etc/ld.so.cache~: Read-only file system
$ sh -c ': > /etc/ld_test_tmp && echo write-ok'
write-ok                                          # 同一个 shell、同一个目录，可写
$ file /sbin/ldconfig.real
ELF 64-bit LSB executable ... statically linked   # 静态 → 没有 PLT → shim 无从上手
```

`/sbin/ldconfig` 是 Ubuntu 的触发器包装脚本，最后一行是 `exec /sbin/ldconfig.real "$@"`。
替换成转发脚本后：

```
$ ldconfig
husk-ldconfig: wrote /etc/ld.so.cache (950 entries from 6 directories)
ldconfig rc=0
$ dpkg --configure -a
Setting up libc-bin (2.39-0ubuntu8.12) ...
husk-ldconfig: note: '-r' is not applied inside the runtime
husk-ldconfig: wrote /etc/ld.so.cache (950 entries from 6 directories)
rc=0
```

## 4 · bug 4：apt 升级 libc6 会静默拆掉运行时（FACT）

dpkg 自己的日志就写着：

```
Unpacking libc6:arm64 (2.39-0ubuntu8.12) over (2.39-0ubuntu8.7) ...
```

装完包以后，guest 里的 libc 变成 stock（1722920 B，`sha256 2544e790…`），
运行时那份带补丁的（1777664 B）没了。症状链条：

```
$ getent shadow husk | cut -d: -f2        # 空
$ python3 -c 'import pwd; print(pwd.getpwnam("husk").pw_name)'
husk                                       # passwd 库正常
```

C 程序直接问 glibc（`tmp/nss2.c`）：

```
getgrnam(sudo)      = found errno=0
getpwnam(nosuchuser)= NULL  errno=0            # 库被问过了，只是没这个人
getspnam(husk)      = NULL  errno=2 (ENOENT)
dlsym(_nss_files_getspnam_r) = ok
  status=-1 errno=0 pwdp_len=0                 # NSS_STATUS_UNAVAIL：模块打不开文件
```

`fopen("/etc/shadow")` 在同一个进程里是能开的（`r`/`rc`/`rce` 三种模式都试过），
所以不是权限，是 nss_files 在 **libc 内部**调 `__nss_files_fopen`：那条调用没有 GOT 槽，
只有打过 slot 页的 libc 才会把它交回 shim。补丁丢了 → 它按 host 路径找 `/etc/shadow`
（Android 上没有）→ ENOENT → 返回空。

2.0 的 sudo 修复脚本因此死在最后两行：

```
+ user_hash=            # getent shadow husk | cut -d: -f2
+ root_hash=
+ [ -n  ]
+ exit 1
```

桌面的报错是 `/bin/sh: 1: Cannot fork`（`ensureSudoInstalled` → `runAsRoot`）。
这一条**不是**进程数/内存不够：同一个 `runAsRoot` 用的 argv、cwd、`env -i` 环境，
手工在 adb 里复现，fork、子 shell、管道全部正常（`tmp/forktest.sh`：20 次 fork 0 失败、
python `os.fork()` 50 次全成）。它只是最终失败点，根因在 bug 4。

重打补丁后：

```
getspnam(husk) = found errno=0 (Success)
  status=1 errno=0 pwdp_len=106
$ getent shadow husk | cut -d: -f2 | wc -c
106
```

桌面随之起来：GNOME 46 X11（`DISPLAY=:0`）、顶栏时钟、dock、桌面图标全部在屏。

## 5 · 为什么值得写进文档：这是**发布级**的坑

`apt upgrade` 是 Linux 用户的第一件事。它会把 libc6 换成 stock，
此后 guest 里的 NSS（`getent shadow`、`sudo` 的用户查询）、以及 `clone3` 的 ENOSYS 兜底
都会静默失效，而且**没有任何报错指向真正的原因**。

所以：
- 打补丁的链路不是一次性操作，`tools/guest-config/install-libc-patch.sh` 是必须存在的工具；
- `docs/LIMITATIONS.md` 要写清楚「升级 libc6 之后必须重跑它」；
- 基准测试之前必须先确认 libc 是打过补丁的那一份（本文件第 4 节的两个命令就是判据）。
