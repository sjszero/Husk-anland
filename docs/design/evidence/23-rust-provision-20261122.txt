evidence 23 - `nr-tools provision`: the toolchain provisioning ported to Rust
2026-11-22   device (serial redacted) PLE110, Android 16, PAGE_SIZE 4096

WHAT WAS PORTED
  tools/device-tests/provision-toolchain.sh was a sh+python3 script:
  parse ports.ubuntu.com Packages.gz, resolve the dependency closure, download
  the .debs, split them with the `ar` format by hand, unpack data.tar.{xz,zst}
  through the python tarfile module, create the generic /usr/bin names, then push
  the tree to the app's private rootfs as a tar stream through `run-as`.

  It is now `nr-tools provision` (Rust, crates/nr-tools/src/provision.rs, ~400
  lines, zero external crates). provision-toolchain.sh is a thin wrapper that
  forwards its environment to the binary; provision-toolchain-legacy.sh keeps the
  old sh+python implementation as the reference the port is checked against,
  reachable with NR_TOOLS=python.

  Deliberately still external processes: gzip/xz/zstd and tar. Every macOS and
  Linux install has them, and pulling in decompression crates would add a
  dependency tree for no benefit. The HTTP transport is std::net::TcpStream with
  a plain HTTP/1.0 GET on port 80 (ports.ubuntu.com answers with 200 and no
  redirect; a Location header back to the same host is followed anyway).

HOW IT WAS CHECKED  (all FACT, run on this host today)

1) Build: cargo build --release -p nr-tools -> OK, no errors.
   (One compile error on the way: `MetadataExt::nlink()` needs the trait imported
   in scope inside the nested `walk` fn. Fixed locally in that fn.)

2) Stage parity, same deb cache, different implementations:
     nr-tools provision --no-push --stage /tmp/nr-toolchain-rs/root
     NO_PUSH=1 STAGE=/tmp/nr-toolchain-sh/root ./provision-toolchain.sh
   Both resolved 53 packages / 55.3 MB and staged 137 entries in usr/bin.
   Full tree compare (relative path, file type, sha256 of contents, symlink
   target):
     entries 2866 vs 2866
     content/link differences: 0
     path differences: 8+8, all of them the *same* pair of files differing only
     in letter case (usr/include/linux/netfilter/xt_connmark.h vs xt_CONNMARK.h,
     ... ipt_ecn.h vs ipt_ECN.h, ...). linux-libc-dev ships both; this Mac's
     filesystem is case-insensitive, so only one can exist and which one survives
     depends on extraction order. Not a porting difference and not observable on
     ext4/EROFS inside the rootfs.

3) The wrapper itself, end to end:
     NO_PUSH=1 STAGE=/tmp/nr-toolchain-w/root ./provision-toolchain.sh
   Same result: 2866 entries, 0 content differences against the shell stage.

4) Real push with the Rust tool:
