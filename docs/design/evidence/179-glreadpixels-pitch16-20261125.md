# 179 · `glReadPixels` 多行读回：目的行距恒为 16 字节

日期：2026-11-25 08:05（CST）。设备 RMX3357（MT6893 / Mali-G77 MC9 / Android 13），
应用 `com.linuxhub.myth.husk`，rootfs `distributions/ubuntu-24.04/rootfs`
（Mesa 26.3.0-devel，FristOneRR 1.2.0）。

evidence 162 记的是现象：16×16 整块读只写「第一行 + 第一列」，32 个像素。这一轮把**地址学**
量出来了，并且给了**能绕过去的方法**。

探针：`gl-probe readback [WxH]`（`runtime/crates/gl-probe`，Rust，`dlopen` 取 EGL/GLES，
guest 里不需要头文件和开发包）。

## 做法

1. `EGL_PLATFORM_SURFACELESS_MESA` + 1×1 pbuffer 起上下文；
2. 造一张 **每像素唯一色** 的 RGBA8 纹理并挂到 FBO 上：
   `R = x*7+3`、`G = y*11+5`、`B = (13x+17y) % 251`、`A = 255`；
3. 读进预填 `0xAA` 的缓冲区，逐个线性偏移问：「这个位置被写了吗？写的值是**原来哪一格**的？」
   —— R/G 在宽度 < 37 时可反解出源坐标，所以不用猜；
4. 四种读法各来一遍：整块 `W×H`、逐行 `W×1` × H 次、逐列 `1×H` × W 次、单点 `1×1` 采样。

## 结果（FACT）

| 尺寸 | 整块读被写 | 其中值正确 | 逐行 `W×1` | 单点 `1×1` |
|---|---|---|---|---|
| 16×16 | 76/256 | 4/256 | **256/256 正确** | 5/5 正确 |
| 32×8 | 60/256 | 4/256 | **256/256 正确** | 5/5 正确 |
| 8×32 | 132/256 | 4/256 | **256/256 正确** | 5/5 正确 |

地址学（16×16 的实测解码，不是推测）：

- **目的行距恒为 16 字节**，与图像宽度无关。32×8 与 8×32 一样落在 16。
- 写入总量 = `H×16 + (W×4 − 16)` 字节。16×16 = 256 + 48 = 304 字节（76 像素），
  32×8 = 128 + 112 = 240 字节（60 像素），8×32 = 512 + 16 = 528 字节（132 像素），三处都对上。
- 于是每行只有**前 4 个像素**落在该去的地方：线性偏移 0–3 是 `src(0..3, y=0)`（这就是
  「值正确 4/256」的那 4 个），4–7 是 `src(0..3, 1)`，……12–15 是 `src(0..3, 3)`。
- 最后一行剩下的 `W×4 − 16` 字节被**连续**写在行距之外：16×16 的偏移 64–75 是
  `src(4..15, 15)`，一眼能看出来是「尾巴顺着贴上去」。

改 pack 参数救不回来：

| 设置 | 整块读被写 | 值正确 |
|---|---|---|
| 默认（`PACK_ALIGNMENT=4`） | 76/256 | 4/256 |
| `PACK_ROW_LENGTH=W` | 76/256 | 4/256（无变化） |
| `PACK_ALIGNMENT=1` | 16/256 | 0/256 |

窄读也不对：逐列 `1×16` 在 Husk 下只写 4 字节、值全错；在 proot 下写到第 244 字节
（16 字节行距的同一个模型，`15×16+4`），同样全错。

## 归属（FACT）

| 对照 | 整块读 | 逐行读 | 结论 |
|---|---|---|---|
| zink → PanVK（GPU） | 76/256，4 正确 | 256/256 | 与软件一样 |
| llvmpipe（软件） | 76/256，4 正确 | 256/256 | — |
| proot + llvmpipe（不经 Husk loader / path-shim） | 76/256，4 正确 | 256/256 | 与 Husk 一样 |

三个都一致，所以这个缺陷**不在** path-shim、**不在** Mali/PanVK 后端；它落在这版 Mesa 的
公共读回（pack / transfer）层或更下面。**具体到哪个文件：UNKNOWN**——要定位得有这版 Mesa
的源码和一次断点，本轮没做。

## 影响与绕法

- 影响：任何「整块 `glReadPixels` = 截图」的工具（截图、录屏、像素比对脚本）在这棵树上
  拿到的是错位画面，而且 `glGetError()` 是 0——不报错。这正是最容易把「读回缺陷」误判成
  「渲染没出来」的坑。
- 绕法（实测 100% 正确）：**一行一行读**（`W×1` 调 H 次），或者干脆逐像素 `1×1` 读。
  `gl-probe` 的 `es3` / `window` 探针一直就是这么读的（evidence 162 的教训）。
- 不要用 `1×H` 顶替：单列读同样是坏的，proot 下还会写到缓冲区之外 180 字节。

- 只测了这一版 Mesa（26.3.0-devel / FristOneRR 1.2.0）与这台设备；换 Mesa 版本是否也有，
  **UNKNOWN**。
