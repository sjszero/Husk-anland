# 130 · 终端式安装路径：`install-husk.sh` + `husk-session.sh` 实测（目标 E 段）

> **范围说明（2026-11-24 补记）**：本文写作时把「Termux 里也能装」当成目标之一。现已作废——
> Termux **不是** Husk 的交付形态，也不承诺可用：guest 树所需的二进制与库 Termux 的 `$PREFIX`
> 不提供，在 Termux 里跑到解包之后就因缺依赖失败（实测）。有效结论只有一条：**在本应用私有目录
> （`run-as .../files/...`）里装、生成启动器、能 exec**，这部分已上机验证。下文中凡是 Termux
> 分支的"预期/形状一致"一律按 UNKNOWN 处理，不再作为验收项。

日期：2026-11-23　设备：RMX3357（`UKHMMB8PYTGECMNV`），`run-as com.linuxhub.husk`，
安装目标 `files/termux-test`，loader `files/libld6.so`（= `tools/loader/ld-embedded.so` 最新版），
rootfs 源 `files/base.tar`。

## 0 · 结论（FACT）

一条命令装完并起会话，不需要 root、不需要逐个 adb 推文件、不涉及 ptrace：

```sh
sh install-husk.sh --rootfs <tarball | http(s) URL> --dest <目录> --loader <libld.so> [--user NAME]
./husk usr/bin/bash -c 'id; head -1 /etc/os-release'
```

产物只有三样：`<dest>/`（rootfs）、`<dest>/../husk`（启动器）、`<dest>/../husk-session.sh`。
本机 app 私有目录里端到端跑通；**真 Termux UNKNOWN**（本机没装 Termux，且 adb shell 里没有
`curl`/`wget`，只有 toybox，所以 URL 分支是在 macOS 上验的，见 §6）。

## 1 · 先记两个事实更正（都是本轮踩出来的，别重犯）

### 1.1 2.0 的 `ubuntu-base-24.04.4-base-arm64.tar` 其实是 gzip，文件名骗人（FACT）

```
$ head -c 8 ubuntu-base-24.04.4-base-arm64.tar | od -An -tx1
 1f 8b 08 08 21 99 d3 6a          ← gzip 魔数
$ md5 -q ubuntu-base-24.04.4-base-arm64.tar
 0be8b9e55eb51de66baa0108b481e865
 31 279 008 B（再 gzip 一层是 30 694 659 B）
```

GNU tar 1.35 自己嗅探压缩，所以 `tar -tf` 能用；toybox tar 也能（pass 1 实测解开了）。
**我一度据此判定"shim 的 read 有 bug"**：同一个文件 `head -c 8` 读到 gz 头、`md5sum` 却"对"。
实际是文件本身就是 gz——`gzip -dc X | md5sum` 与 `md5sum X` 相等，是因为两个 X 是同一个 gz 的
两份拷贝。**零 shim bug**，这一条是我自己的误判，记在这里防止下次再查一小时。

INFERENCE（未验证）：2.0 的 `offline/*.tar` 大概率是同一批打包方式。装 Husk 之前先
`od -An -tx1 -N6` 看一眼前 6 字节，再决定要不要解压。

### 1.2 mksh/dash 在 `run-as` 下没有可写的 TMPDIR（FACT）

`$(...)` 捕获和 heredoc 都要临时文件；`/tmp`、`/data/local` 在 app 域都不可写，症状是
`can't create temporary file /data/local/shXXXX.tmp: Permission denied`，而且是在脚本跑到一半时。
脚本现在自己挑：`$TMPDIR` → `$DEST/tmp` → `$OUT/tmp`，取第一个可写的导出。

### 1.3 toybox tar 是会嗅探 gzip 的（补测，别记错）

```
$ (gzip -dc base.tar | tar xf - -C ttpipe); echo $?
tar: can't link 'usr/bin/perl5.38.2' -> 'usr/bin/perl': Permission denied
tar: had errors
1                                    ← 只有硬链接失败，解包本身成功
```

之前那次 `tar: short header` 是喂了 **gz 套 gz**（我自己 `gzip -c base.tar` 造的 `base.tar.gz`），
不是 toybox 不会读管道。脚本仍然自己做魔数解压（xz/zstd 它确实不解，且 Termux 的 tar 又是另一套），
但理由是"统一一条路径 + 能把 gz 套 gz 报清楚"，不是"toybox 不能"。

## 2 · 脚本里修掉的实现缺陷

| 缺陷 | 后果 | 改法 |
|---|---|---|
| 启动器把 `"$0"` 当 rootfs 传参 | `$0` 是启动器自己，会去 `cd` 一个文件 → 起不来 | 安装期把 rootfs/loader 的绝对路径写进启动器 |
| 启动器没给 `NR_LD` | `husk-session.sh` 回落到 `dirname(rootfs)/libld.so`，本机叫 `libld6.so` → `loader not executable` (69) | 启动器里 `NR_LD=… exec …` |
| 复制 `husk-session.sh` 用 `$DEST/..` | 源和目标是同一个文件时 `cp` 报错 + `set -e` 中断 | 先解析 `OUT=$(dirname "$DEST")`，同文件就跳过 |
| 硬链接自检用 grep 匹配整段输出 | 匹配到了 `cannot access '/usr/bin/perl5.38.2'` 这句错误，**文件缺失反而判通过** | 改成在 guest 里 `test -s` 两个文件，只认 `yes` |
| 压缩输入直接 `tar xf` | toybox tar 从管道吃不动压缩流（`short header`） | 魔数嗅探 gz/xz/zstd → 先解到 `$OUT/.husk-pass1.tar` → 再 tar；解完仍是压缩则报 67（gz 套 gz） |
| URL 先被当路径 `cd` | `cd: http://…: No such file` | `is_url` 分支跳过路径规范化，下载后再变成路径 |

## 3 · 为什么必须解两遍（FACT）

```sh
$ sh install-husk.sh --rootfs base.tar --dest termux-test --loader libld6.so
== pass 1: extract (hard-link errors are expected) ==
   (gzip -dc -> …/.husk-pass1.tar)
   tar: can't link 'usr/bin/perl5.38.2' -> 'usr/bin/perl': Permission denied
   tar: can't link 'usr/bin/uncompress' -> 'usr/bin/gunzip': Permission denied
   tar: had errors
== pass 2: re-extract through the shim (fixes hard links) ==
== verify ==
   PRETTY_NAME="Ubuntu 24.04.4 LTS"
   bins=294
   -rwxr-xr-x. 1 10302 husk10302 3942240 … /usr/bin/perl5.38.2
   -rwxr-xr-x. 1 10302 husk10302    2346 … /usr/bin/uncompress
== ok: hard links materialised (perl5.38.2 + uncompress are real files) ==
```

pass 1 丢两个名字（SELinux 拒 `link(2)`），pass 2 走 shim 的 `link()` → 复制回退补上。
这不是安装器的特例：dpkg 依赖同一个回退。

## 4 · 启动器实测（从任意 cwd，FACT）

```
A) launcher from /                uid=0(root) gid=0(root) groups=0(root)
                                  /root
                                  PRETTY_NAME="Ubuntu 24.04.4 LTS"
B) default = login shell          login-shell
                                  /root
C) --cwd /usr/bin                 /usr/bin
D) --user hu1 on rootfs-full      uid=1000(hu1) gid=1000(hu1) groups=1000(hu1)
                                  /home/hu1
E) absolute program path          abs-ok
```

`--cwd` 以前是"解析了但没用"：`husk-session.sh` 只在宿主侧 `cd "$ROOTFS"`，与 guest 的 cwd 无关。
现在用 `usr/bin/env -i -C "$CWD"`——`env` 本身跑在路径层里，`-C` 才是 guest 的 chdir。
同时把程序路径规范化成绝对路径（`env -C` 之后相对路径的基准变了）。

## 6 · URL 分支（macOS 上验，本机设备侧 UNKNOWN）

```
$ python3 -m http.server 8899 --bind 127.0.0.1 &
$ sh install-husk.sh --rootfs http://127.0.0.1:8899/ubuntu-base-24.04.4-base-arm64.tar \
      --dest /tmp/urlfetch/root --loader /usr/bin/true
== download ==
   from : http://127.0.0.1:8899/ubuntu-base-24.04.4-base-arm64.tar
100 29.8M  100 29.8M … 192M
   saved: /tmp/urlfetch/ubuntu-base-24.04.4-base-arm64.tar      md5 0be8b9e5… ✓
install-husk: cannot execute the loader from here:               ← 故意用 /usr/bin/true 当 loader
```

下载、命名、落盘、md5 都对；之后停在 loader 探针（macOS 上跑不了 aarch64 的 loader，预期）。
设备侧 URL 分支没有 curl/wget 可用，**UNKNOWN**；Termux 自带 curl，形状与上面一致。
