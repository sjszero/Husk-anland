# 174 · 把窗口 swap 拆成「GPU 渲染」和「呈现」两段：呈现占 85%–95%

日期：2026-11-25 07:1x–07:3x（CST）。设备 RMX3357（MT6893 / Mali-G77 MC9 / Android 13），
应用 `com.linuxhub.myth.husk`，X server `:0`（X.Org 21.1.99，跑在应用自己的 `:x11` 进程里）。
这次**没有**跑 gnome-shell：探针自己开一个窗口，所以量到的是「客户端 → X server」这一跳，
不含合成器再合成一次的成本。

## 为什么要做

`docs/LIMITATIONS.md` §7 之前写的是「640×480 上 zink 131 fps、llvmpipe 300 fps，瓶颈是那次
SHM 拷贝」。这句话是**推断**，没做过拆分：窗口 swap 里同时有 GPU 渲染、GPU→CPU 回读、
挂到 X server 的拷贝、server 侧导入。不拆开就不知道要不要为「零拷贝」动手。

## 做法

1. `gl-probe` 加了两个参数（`window WxH N` 之前写死 640×480 / 60 帧）和一个新子命令
   `pbuf WxH N`：同一套 EGL/GL，改成 surfaceless display + 同尺寸 pbuffer，同样的
   clear+swap 循环，**每帧 `glFinish()`**；
2. 两种渲染器各跑一遍：`GALLIUM_DRIVER=zink`+PanVK ICD，和 `GALLIUM_DRIVER=llvmpipe`；
3. 尺寸 160×120 / 320×240 / 640×480 / 960×960 / 1080×1080，每档 60 帧；640×480 与
   1080×1080 各重复一次看抖动；
4. 屏幕保持点亮（`svc power stayon usb`），窗口尺寸都在屏内（1080×2400）。

没有 `glFinish` 的第一版 pbuffer 量到 0.1 ms / 60 帧 —— 那只是把 Vulkan 命令录进队列，
一个像素都没画。这一条记下来：**离屏基线不带同步就是假数字**。

## 数字（ms/帧，60 帧平均）

| 尺寸 | 像素(M) | zink window | zink pbuf | llvmpipe window | llvmpipe pbuf |
|---|---:|---:|---:|---:|---:|
| 160×120 | 0.019 | 4.04 | 1.22 | 1.07 | 0.36 |
| 320×240 | 0.077 | 4.52 | 1.14 | 1.57 | — |
| 640×480 | 0.307 | 8.49 / 9.80 / 10.19 | 1.28 | 4.28 | 0.71 |
| 960×960 | 0.922 | 23.64 | 1.65 | 12.50 | — |
| 1080×1080 | 1.166 | 28.84 / 30.68 / 32.15 | 1.70 | 13.00 | 1.05 |

差值（window − pbuf）= 呈现这一段，按窗口面积折算：

| 渲染器 | 640×480 差值 | 1080×1080 差值 | 每兆像素 |
|---|---:|---:|---:|
| zink (PanVK) | 7.2–8.9 ms | 27.1–30.5 ms | **≈ 24.8 ms/MP** |
| llvmpipe | 3.6 ms | 12.0 ms | **≈ 11 ms/MP** |

## 能说明什么（FACT）

- **GPU 渲染本身跟尺寸几乎无关**：zink 从 160×120 到 1080×1080（60 倍像素）只是 1.22 → 1.70 ms。
  所以「GPU 算力不够」不成立，`LIMITATIONS` §7 那条判断方向是对的。
- **窗口 swap 的成本按窗口面积线性长**，斜率 24.8 ms/MP（zink），折算约 4 B/px → **≈ 161 MB/s**
  的有效带宽。这是「读了像素、搬了像素」的量级，不是 GPU 算力。
- **zink 的呈现成本是 llvmpipe 的 2.4 倍/像素**。所以那段成本不只是「一次拷贝」：llvmpipe 的结果
  本来就在 CPU 内存里，zink 还得先把 tiled 的 GPU 表面回读/转成线性再交给 X。
  也就是说 640×480 那 8.9 ms 里，GPU 只占 1.3 ms，剩下是**回读 + 拷贝**。
- 之前 README/Release 里「131 fps 输给 300 fps」的对比，瓶颈确实在呈现链，不在 GPU —— 这次是
  减法量出来的，不是推断。

## 不能说明什么

- 没跑合成器：真桌面里还有 mutter 再合成一次，成本只会更高，不会更低。
- 没有分离「回读」和「X 拷贝」各自多少：要分离得再做一个把 GPU 表面直接落到线性 map 的变体。
- 不含 Android 侧 `AHardwareBuffer → SurfaceControl`（那段 evidence 59 测过是零拷贝）。

## 对路线的意思（INFERENCE）

1. 零拷贝能拿回的是 zink 那 ≈ 24.8 ms/MP 里的绝大部分：1080×1080 从 ~30 ms 降到个位数是可期的。
2. 但这台机上**DRI3 做不出来**：X server 是应用进程里的 bionic Xorg，`untrusted_app` 打不开
   `/dev/dri`，`/dev/dma_heap` 不存在、`/dev/ion` EACCES → 服务器没有 DRM 设备，DRI3 只能是
   广告出来然而「Could not get DRI3 device」。这属于 shell（X server）那一层的能力，不是
   `path-shim` 能补的。
3. 所以在当前架构下可选的是：给 X server 造一条能 import dma-buf 的路（要 shell 侧配合），
   或者接受这次拷贝并把它写清楚。**不要再用「换个合成器/上 Wayland」来解**——那条已经否决。

## 再拆一层：回读和传输各占多少（同一天追加）

上面的减法只分出「渲染 / 呈现」，呈现那一段里还有两件事：GPU 把 tiled 表面回读成线性像素，
以及把像素交给 X server。再加一个只做第二件的基线：`gl-probe xput WxH N`，完全不碰 GL ——
一个客户端 32 位缓冲（自己填的图案）用 `XPutImage` 打到同尺寸窗口，每帧 `XSync`，60 帧计时。

| 尺寸 | xput（纯 X 传输） |
|---|---:|
| 160×120 | 1.65 ms/帧 |
| 640×480 | 3.90 ms/帧 |
| 1080×1080 | 8.08 ms/帧 |

把它填进上面的表（ms/帧）：

| 项 | zink 640×480 | llvmpipe 640×480 | zink 1080×1080 | llvmpipe 1080×1080 |
|---|---:|---:|---:|---:|
| GPU 渲染（pbuf） | 1.28 | 0.71 | 1.70 | 1.05 |
| X 传输（xput） | 3.90 | 3.90 | 8.08 | 8.08 |
| 两项相加 | 5.18 | 4.61 | 9.78 | 9.13 |
| 实测 window | 8.49–10.19 | 4.28 | 28.84–32.15 | 13.00 |
| **残差（GPU→CPU 回读等）** | **3.3–5.0** | **−0.33** | **19.1–22.4** | **3.9** |

**对照组说明模型成立**：llvmpipe 的像素本来就在 CPU 内存里，没有回读这一步，所以
`pbuf + xput` 与实测 window 对得上（640×480 残差 −0.33 ms，即噪声）。zink 多出来的
3.3–5.0 ms（640×480）和 19–22 ms（1080×1080）就是 GPU 表面的回读，折算 11–16 ms/兆像素，
即 ~230–280 MB/s。

于是 640×480 那一帧 9.5 ms 的构成是：**GPU 1.3 ms（14%）+ X 传输 3.9 ms（41%）+ 回读 4.3 ms（45%）**。

这条对零拷贝的意义：DRI3/dma-buf 直传一次拿走「传输 + 回读」这 86%，剩下的基本就是 GPU 那
1.3 ms。反过来说，只要还在走 SHM，无论怎么调环境变量，天花板就在 3.9–8 ms/帧这一档。

## 追加的不能说明什么

- `xput` 用的是 depth24 的窗口（EGL surface 的深度可能不同），且没有走 MIT-SHM 的客户端侧
  共享段（`XPutImage` 走请求/数据流）。真正的 SHM 客户端路径可能更快，也就是说「传输」这一格
  还有下探空间——但没测，不写进来。
- 残差里除了回读，也可能含 X server 侧的导入/合成差异，两者没有再分离。

## 拉回日常分辨率（2400×1080），再加一个 GPU 型负载

前面最大只测到 1080×1080 = 1.17 兆像素，而这台机的 X 屏幕本身就是 **2400×1080 = 2.59 兆像素**
（`xdpyinfo`：`dimensions: 2400x1080 pixels`）。日常用的是后者，所以按它重测：

| 项（ms/帧，2400×1080） | zink (PanVK) | llvmpipe |
|---|---:|---:|
| window（清屏 + 呈现） | 50.18 | 20.12 |
| pbuf（纯渲染 + `glFinish`） | 2.25 | 2.01 |
| xput（纯 X 传输） | 17.66 | 18.12 |
| **残差（GPU→CPU 回读）** | **30.27** | **−0.01** |

对照组在 2.59 兆像素上依旧对得上（llvmpipe 残差 −0.01 ms），模型成立。zink 那 30.27 ms 的回读
折算 11.7 ms/兆像素，和 640×480、1080×1080 两档算出来的 11–16 ms/兆像素一致。

### GPU 型负载：这里才是加速该出现的地方

`gl-probe fill WxH passes frames`：全屏两个三角形，片元着色器每像素跑 48 次依赖的 `sin()`，
每帧画 `passes` 遍，离屏 pbuffer，每帧 `glFinish`。

| 负载 | GPU（zink→PanVK） | 软件（llvmpipe） | 倍率 |
|---|---:|---:|---:|
| 1280×720，2 遍 | 14.90 ms/帧（67.1 fps） | 101.92 ms/帧（9.8 fps） | **6.8×** |
| 2400×1080，2 遍 | 23.84 ms/帧（41.9 fps） | 266.73 ms/帧（3.7 fps） | **11.2×** |

两档都做了 `(0,0)` 像素回读，非全黑（`93,233,0,255` / `2,251,0,255`），保证 draw 真的落地。

所以四类负载的结论分开写，不混：

| 负载 | 谁更快 | 数字（2400×1080） |
|---|---|---|
| 着色器密集（算） | GPU | 41.9 fps vs 3.7 fps，快 11.2× |
| 纯清屏（离屏，无呈现） | 差不多 | 2.25 ms vs 2.01 ms |
| 清屏 + 窗口呈现 | 软件 | 19.9 fps vs 49.7 fps |
| 路径/syscall 密集（对 proot） | Husk | 见 `docs/BENCHMARKS.md` |

### 这一轮的坑（写下来免得再犯）

- 第一版 `fill` 用 `glGetUniformLocation` 取顶点属性 `p`，返回 −1，属性没绑上 → 三角形塌掉、
  片元着色器根本没跑，llvmpipe 量到 **0.23 ms/帧**的假数字。改成 `glGetAttribLocation` 并加
  像素回读之后才是真数。
- 只有清屏的 `pbuf` 对 GPU 是最不利的负载（工作量为零、每条命令的开销占满），不能拿它当
  "GPU 加速效果"的代表。

## 附：这是「手机慢」还是「路径没共享内存」（同日补测）

一个自然的反驳是「你们这台机内存带宽不行，所以拷贝才 30 ms」。所以把「拷贝」和「带宽」
分开量：guest 里用 `ctypes.memmove` 做纯内存对拷，10 MiB × 30 次
（脚本设备侧 `files/linux/memcp.sh`，走 `NR_ROOTFS=... husk/libld.so --library-path ... usr/bin/python3`）：

```text
memmove 10.05 GiB/s  1.043 ms per 10 MiB
```

按这个带宽，2400×1080 一帧（2.592 兆像素 × 4 B = 10.37 MB）纯值拷贝下限约 **1.0 ms**，
而上面实测的 GPU→CPU 回读是 **30.27 ms/帧**。也就是：

| 解释 | 能解释多少 |
|---|---:|
| 内存带宽不够 | **3.4%** |
| 其余（路径上没有共享内存：CPU↔内核往返、tiled→线性转换、evidence 179 的 pitch 错位 16 B/行） | 96.6% |

所以「换台更快的手机」修不好这件事，能修的是**把共享内存这条路接上**（DRI3/dma-buf，
需要 shell 侧配合，见上文）。

### 这一段是共性还是本机

- **FACT**：本机应用进程是 `untrusted_app`，`open("/dev/dri/renderD128")` → `EPERM`，
  `/dev/dri/card0` 是 shim 合成的 `10,33`，`/dev/dma_heap` 不存在、`/dev/ion` EACCES。
- **INFERENCE**：任何把 X server 关在 Android 应用进程里的方案（Termux:X11、Xvfb 系、
  proot 里的桌面栈）都受同一条约束——DRI3 的前提是 server 自己能拿到 render node 并 import
  dma-buf，这在 `untrusted_app` 下要么靠同 uid、要么靠跨进程传 fd 的通路。差别只在谁把这
  条路打通了。
- **UNKNOWN**：别人在各自实机上到底走通没有、省掉多少，我们没有在他们的机器上量过，
  不替他们宣布。本仓库只写我们量到的数。
