## 1 · 为什么之前死在 `eglMakeCurrent`

`164` 记的是事实：`gl-probe window` 在 `stage 6: context OK` 之后立刻 `segv|sig=11`，loader
报 `Instance extension VK_KHR_xcb_surface not supported by available ICDs`。

根因在源码里，不在运行时：`src/panfrost/vulkan/panvk_instance.c:125`

```c
#ifdef VK_USE_PLATFORM_XCB_KHR
   .KHR_xcb_surface = true,
#endif
```

而上一版构建的 `meson configure` 记着 `platforms = []`，`src/vulkan/meson.build:47` 那段
`if with_platform_x11` 整块跳过，`-DVK_USE_PLATFORM_XCB_KHR` 根本没进命令行。所以 ICD
里字符串有、扩展表里没有。

重编命令（Ubuntu 24.04 容器 + aarch64 交叉工具链，其余开关与 `evidence 46` 一致）：

```
meson setup /build/frist-target-x11 \
  -Dbuildtype=release -Dplatforms=x11 -Dgallium-drivers= -Dvulkan-drivers=panfrost \
  -Dpanfrost-kmds=kbase -Dtools= -Dllvm=disabled -Dvideo-codecs= -Dzstd=disabled \
  -Dmesa-clc=system -Dinstall-mesa-clc=false -Dprecomp-compiler=system \
  -Dinstall-precomp-compiler=false -Dopengl=false -Dgles1=disabled -Dgles2=disabled \
  -Degl=disabled -Dglx=disabled -Dgbm=disabled -Dpanfrost-rust=false \
  -Ddisplay-info=disabled -Dxmlconfig=disabled -Dlibunwind=disabled -Dlmsensors=disabled \
  -Dvalgrind=disabled -Dspirv-tools=disabled --cross-file=/build/aarch64-cross.ini
```

x11 平台要多一套 aarch64 的 xcb 头/库（`libxcb1-dev`、`libx11-xcb-dev`、`libxcb-dri3-dev`、
`libxcb-present-dev`、`libxcb-xfixes0-dev`、`libxcb-sync-dev`、`libxcb-randr0-dev`、
`libxcb-shm0-dev`、`libxcb-keysyms1-dev`、`libxshmfence-dev`，以及 `libxrandr-dev`、
`libxext-dev`、`libxfixes-dev`、`libxdamage-dev`、`libxrender-dev`）。第一次配置就卡在
`Run-time dependency xrandr found: NO`，装完才过。

## 2 · 桌面为什么会崩在 MIT-SHM

用上新 ICD 之后 gnome-shell 能起来，但几秒后死：

```
Mtk-ERROR **: Received an X Window System error.
The error was 'BadAccess (attempt to access private resource denied)'.
  (Details: serial 1840 error_code 10 request_code 130 (MIT-SHM) minor_code 1)
```

写了 40 行探针（dlopen `libX11`/`libXext`，不装头文件）量这条边界：

```
XOpenDisplay OK
XShmQueryExtension = 1
MIT-SHM version 1.2 pixmaps=1
shmget(IPC_PRIVATE,4096) = 45 errno=17
shmat -> 0x7252f37000
XShmAttach -> 1 shmseg=14680065 server_error=(10, 33281)
SHM-CROSS-PROCESS: REJECTED
```

机理：这个内核没有 SysV IPC（`path-shim/src/lib.rs` 里那一段注释就是为它写的），
guest 的 `shmget`/`shmat` 由 shim 用**文件 + mmap** 模拟（`/run/husk/ipc/shm/<id>`）。
而 X server（Lorie）在 App 进程里、在 guest 外，它收到的是协议里的整数 `shmid`，
只能用真内核 `shmat(id)` —— 那个 id 在内核里不存在，回 `BadAccess`。

打算的修法：shim 里让 `XShmQueryExtension` 返回 0，让客户端走自己的拷贝路径（`XPutImage`），
不在 attach 上撞死。跨进程真共享要等 fd 版 attach（MIT-SHM 1.2 有 `ShmAttachFd`，
但 Xlib 不暴露；翻译请求得手写协议），列入未做。

`runtime/crates/path-shim/src/lib.rs`：`XShmQueryExtension` + `boot.rs` 的 `BODY_PATCH` 表。

### 2.1 这条修法**没有验证生效**（2026-11-24 补测）

```
$ shmchk（ctypes + dlsym，新 loader）
XShmQueryExtension=1
$ shmchk（旧 loader）
XShmQueryExtension=1
```

也就是说：shim 里那个返回 0 的桩函数**没有被这条调用路径命中**。桌面不再崩是事实（§4 抓到了
完整桌面、跑了一小时量级的会话日志无 XError），但**不能**说成"我们把 MIT-SHM 关掉了"。
两个可能，均未验证：
1. `dlsym(RTLD_DEFAULT)` 直接解析到 libXext 自己的定义，绕开 GOT 改写（这条测试本身可能无效）；
2. zink/kopper 与 mutter 实际没走 XShm 那条路，崩的那次是另一处触发。

下一步要么写一个**直接调用** `XShmQueryExtension` 的探针（不经 dlsym），要么去查 mutter 源码里
BadAccess 那次的具体调用点。在那之前，这一条按 UNKNOWN 记账。

## 3 · 假 DRM 节点必须"像"设备

`/dev/dri/renderD128` 一直是 shim 造的假节点（打开拿一个假 fd，`mmap` 转到 `mali0`）。
问题在**它 stat 出来是什么**：libdrm/udev 拿到一个节点后第一件事就是 `fstat` 取设备号，
再去 `/sys/dev/char/<maj>:<min>/device/uevent` 和 `/sys/class/drm/<node>/` 查它是谁。
原来的假节点是一个普通文件，这两步都指向"不是 GPU"，于是：

- Chromium/Electron 的 GPU 进程认为没有 GPU，退回软件合成；
- GStreamer 的 VA 插件按 udev 路径找设备，找不到。

本轮补了三件事（都在 shim，不用 preload、不用 ptrace）：

1. `stat` / `statx` / `fstat` 对 `/dev/dri/renderD128`、`card0` 和假 fd 一律回
   **字符设备 + 真 `/dev/mali0` 的 major:minor（10:33）+ 0666**；
2. 合成 `/sys/dev/char/<maj>:<min>/device/uevent`（`DRIVER=mali` + `OF_COMPATIBLE_0=…`）；
3. 合成 `/sys/class/drm/renderD128/{dev,uevent}`，以及 `/proc/bus/pci/devices`（空表——
   这台设备没有 PCI 总线，而 Chromium 把"枚举不到 PCI"当成"没有 GPU"）。

实测（`xe-sysfs.sh usr/bin/bash -c …`）：

```
$ stat -c "%F %t:%T %a %n" /dev/dri/renderD128 /dev/dri/card0
character special file a:21 666 /dev/dri/renderD128      # a:21 = 10:33
character special file a:21 666 /dev/dri/card0
$ ls -l /dev/dri/
crw-rw-rw-. 1 root root 10, 33 Jan  1  1970 card0
crw-rw-rw-  1 root root 10, 33 Jan  1  1970 renderD128
$ cat /sys/class/drm/renderD128/dev
10:33
$ cat /sys/class/drm/renderD128/uevent
MAJOR=10 / MINOR=33 / DEVNAME=dri/renderD128 / DEVTYPE=drm_minor
$ wc -c < /proc/bus/pci/devices
0
```

**没有解决**：`MESA-EGL: warning: DRI3 error: Could not get DRI3 device` 依旧。
客户端仍在 SHM 拷贝路径上，不是 dmabuf 直出。下一步要么让 `drmGetDevice2(fake_fd)`
整条走通（还缺 `device/drm/` 目录与 `subsystem` 链接），要么在 X server 侧解决。

## 4 · 出帧证据：抓 X 根窗口，不是抓手机屏幕

手机 `screencap` 抓的是 App 自己的 UI（它此刻显示的是"GNOME 已退出"那块），不能当 guest
的证据。所以给 `gl-probe` 加了 `root` 子命令：`XGetImage` 读 X 根窗口，写 PPM，再打印
非黑像素数与直方图。同一次会话里：

```
$ gl-probe root /tmp/root.ppm
root 2400x1080 window=1297
image 2400x1080 stride=9600 bpp=32
nonblack=2592000/2592000 (100.0%) histogram=[81212, 63184, 98888, 596836, 1378332, 322148, 4549, 46851]
wrote /tmp/root.ppm
```

100% 非黑、直方图铺开，转成 PNG 后就是完整桌面：壁纸、顶栏时钟（21:44）、dock、
桌面图标（主目录 / 回收站）、一条"Logged in as a privileged user"的通知。

会话日志同一时刻的渲染器只有一种：

```
GL=zink cogl=gles2 jit_off=1 override=3.2
FristOneRR 1.2.0 (Mesa 26.3.0-devel)      # ×2，无 llvmpipe
```

## 5 · 复现

```
# 1. loader（含 XShmQueryExtension=0、假节点 stat/statx/fstat、DRM sysfs）
NDK=<ndk>/bin make loader

# 2. 放到设备上（新文件名，避开正在跑的老 loader 的 ETXTBSY）
adb push app/app/src/main/jniLibs/arm64-v8a/libld.so /data/local/tmp/libld.so
adb shell "run-as com.linuxhub.myth.husk sh -c 'cp /data/local/tmp/libld.so files/linux/husk/libld-sysfs.so; chmod 755 files/linux/husk/libld-sysfs.so'"

# 3. 会话（zink + ES3 override）
HUSK_GL=zink COGL_DRIVER=gles2 HUSK_GLES_OVERRIDE=3.2 sh files/linux/husk-x11-gpu3.sh

# 4. 出帧证据
sh files/linux/xe-sysfs.sh usr/bin/env DISPLAY=:0 /tmp/gl-probe root /tmp/root.ppm
```
