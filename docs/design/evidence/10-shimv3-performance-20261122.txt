# Reading of the numbers (honest caveats included)
#
# 1) Process creation is dominated by loader work, not by the shim. 200 execs of the
#    trivial /usr/bin/true: 0.4-0.9s with plain ld.so, 3.7-5.2s with any LD_PRELOAD at
#    all. The libgmp.so.10 control (a 2.5MB unrelated preload) costs the same 4.4-4.7s,
#    so this is preload/ld.so cost on /data (Android 16), not path resolution.
#    Same experiment with the shim placed in /data/local/tmp gave 2.2s/200 vs 3.9s/200,
#    i.e. the app-private files dir is the slow part. UNKNOWN: exact kernel-side reason.
#
# 2) Whole-loop numbers on this phone swing ~2x run to run (thermal / background load),
#    so only the in-process rows are stable enough to compare.
#
# 3) In-process path work is what a shell/package manager actually pays:
#      2000 x stat("/etc/os-release")        native 0.02s   shim 0.03-0.05s  (+5..15us/op)
#      2000 x stat(deep 4-component path)    shim   0.04-0.06s                (~20us/op)
#      2000 x open("/etc/os-release")        native 0.03s   shim 0.04-0.07s  (+5..20us/op)
#    A resolve is 2-5 raw syscalls (readlinkat for cwd, readlinkat per component,
#    openat with O_PATH, dup/close), so ~5us/op is the expected order of magnitude.
#
# 4) Against PRoot (ptrace; evidence 05, RMX3357): PRoot traps *every* syscall of
#    *every* process at ~50-100us each. Here nothing is trapped; only the libc entry
#    points we replace pay, and only they pay for the resolve. The win is structural,
#    not a constant factor on the same work.
#
# 5) Known cost still on the table: execve() re-resolves the binary and re-execs through
#    ld.so --library-path, and ld.so then stats its way through every NEEDED library via
#    our hooks. Caching (fd -> resolved path, direct vDSO-free fast path for /usr/bin/*)
#    is the obvious next optimization; not attempted yet.
