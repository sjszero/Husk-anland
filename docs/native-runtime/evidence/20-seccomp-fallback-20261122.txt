THE QUESTION
  Until evidence/17 the in-loader SIGSYS handler was never installed: the embedded
  shim has no .init_array that the loader would run, so install_sigsys() had to be
  called from nr_boot. Before that fix, NR_SIGSYS=enosys "worked" only because the
  handler was never there to change anything - i.e. the mode was untested. The plan
  therefore carried it as "probe only". This file settles it with direct evidence.

TEST (tools/native-runtime-tests/sigsys-check.sh)
  A C program compiled in the guest calls the two optional syscalls this ROM traps
  (set_robust_list=99, rseq=293) directly, so nothing else in the process can hide
  the result, and prints the return value and errno.

A. NR_SIGSYS=log  (reproduce the policy's own action, but record it first)
  sigsys|code=1|nr=99|arch=-1073741641|mode=1|pc=525594498728|ucpc=440|ra=525595380068|set_robust_list
  rc=159  (159 = 128 + SIGSYS)
  FACT: the handler ran, wrote its record (mode=1 = log), and then reproduced the
  death exactly. Nothing else changed: the harness still sees 128+31.

B. NR_SIGSYS=enosys  (turn the trap into "kernel does not have it")
  sigsys|code=1|nr=293|arch=-1073741641|mode=2|pc=524469835432|ucpc=440|ra=524470716772|rseq
  rseq             nr=293 -> -1 errno=38 =ENOSYS (no kernel support)
  set_robust_list  nr=99  -> -1 errno=38 =ENOSYS
  survived both
  rc=0
  FACT: both traps were converted to -ENOSYS, the caller continued on its documented
  "not implemented" path, and the process completed normally.

C. Whole workloads under NR_SIGSYS=enosys (not just the probe)
  01-functional-matrix.sh   31 PASS / 0 FAIL / exit 0
  accept-gcc-make.sh        gcc rc=0, run rc=0, make rc=0, noop rc=0, clean rc=0
  FACT: the bash+coreutils matrix and the whole gcc/cc1/as/collect2/ld + make pipeline
  run with the handler as the only protection, i.e. with every build-time nop disabled
  in effect (the nops stay in the image, but nothing depends on them being the only
  defence any more).

WHAT IT IS, AND WHAT IT IS NOT (so nobody over-reads this)
  * It IS a verified fallback for exactly the case it was designed for: an *optional*
    syscall whose absence has a documented fallback path in glibc. The kernel's answer
    becomes what a kernel without that syscall would have answered.
  * It is NOT a general syscall emulation layer. If a caller needs the syscall to
    actually work (rseq is the example: glibc will run its slow fallback, but the fast
    path is gone), returning ENOSYS changes behaviour, and there is no way to fake the
    success case from a signal handler.
  * It is NOT the primary mechanism. The default remains: never trap at all (the two
    nop'd sites are chosen because their callers ignore the return value, evidence/15).
    The handler costs one rt_sigaction at startup and zero per call.
  * Consequence for the plan: the "seccomp trap is only a probe" caveat in
    06-sole-plan-t2t1.md §7 is now wrong in one direction and right in another. It is
    a trustworthy fallback for optional accelerators on this ROM (measured above), and
    still not a mechanism one should build coverage on.

CORRECTION TO evidence/16
  evidence/16 said "getrandom(2) is trapped by this ROM's seccomp policy: it kills the
  process with SIGSYS". That is wrong: a direct call in the same domain returns data
  (getrandom=8 bytes, errno=0, exit 0). The temp-name code in the shim still takes its
  six characters from auxv AT_RANDOM, which is the right design (no syscall, no seccomp
  dependency), but the reason given in evidence/16 was not the real one. The conclusion
  in that file (implement mkstemp ourselves so the template stays a guest path) does not
  depend on it.
