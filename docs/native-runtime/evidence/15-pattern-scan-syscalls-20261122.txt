BEFORE: two `svc #0` sites in libc and one in ld.so were addressed by the literal
vaddrs 0x85714, 0xbd510 and 0x106cc. A different glibc, or a recompile with a
different linker, would silently `nop` whatever else happened to be at those
addresses.

NOW: tools/nr-loader-hook/nr-scan-syscalls.py. It
  1. reads the image's .gnu.version_d and refuses any version it was not told to
     expect (`--version`);
  2. finds every `svc #0` and walks *backwards* for the `mov x8,#NR` that selects
     the syscall - glibc sets the argument registers after x8, so the two are not
     adjacent (the ld.so site has six instructions in between);
  3. keeps only the optional accelerators (set_robust_list=99, rseq=293);
  4. requires the first instruction after the `svc` to *write* x0 without reading
     it - i.e. the caller provably ignores the result, which is the only reason a
     `nop` is even meaningful;
  5. requires the site count per syscall to equal the expected count.

If any of that fails it prints REFUSING and exits non-zero; nothing is written.

  The rseq sites are found and deliberately *not* patched: their callers inspect
  the return value (the instruction after the `svc` reads x0), so a `nop` would
  hand the code a stale x0. glibc's own documented switch
  (GLIBC_TUNABLES=glibc.pthread.rseq=0, already used by the harness) keeps that
  path from running. This is stated rather than papered over.
